# OpenHarness — CLAUDE.md

Local-first Windows desktop model loader and runner with **Store** (Hugging Face browser/downloads), **Models**, plain **Chat** with voice, and **Studio** (image / video / speech / transcription generation). Uses llama.cpp, a Python worker and Qwen3-TTS. Agentic work belongs in AI Shuffle. (Formerly "Hangar AI".)

See `README.md` for build and dev instructions.

## Key constraints

- **Svelte 5 runes only** — no `export let`, no `$:`, no store auto-subscription. Use `$state`, `$derived`, `$effect`, `$props`.
- **Streaming via Tauri Channels** — high-frequency token/progress/telemetry streams use `tauri::ipc::Channel<T>`; low-frequency app-wide signals use Events.
- **Single-writer state** — async actors own mutable state; UI reads via subscriptions; no shared `Arc<Mutex<T>>` chains.
- **Desktop-only, Windows-first** — minWidth 1024, NVIDIA CUDA primary + CPU fallback. AMD/Intel and other OSes are post-v1.
- **SQL discipline** — only `sqlx::query!` / `query_as!` macros, never raw string interpolation. All DDL lives in `migrations/`.
- **Local-first, zero telemetry** — never send user data off-device by default. No analytics, no crash reporting unless the user opts in.

## Stack

- Tauri 2.x + SvelteKit (SPA, `adapter-static`, `ssr=false`)
- Rust + sqlx 0.8 + SQLite (WAL) + FTS5
- TailwindCSS 4
- pnpm (single-package, no monorepo)
- llama.cpp pin-and-fetch on first run (not bundled in MSI)
- qwentts.cpp `tts-server` sidecar for Qwen3-TTS talker GGUFs (third engine family)
- nvml-wrapper for VRAM telemetry

- **Loader planner** (2026-11-09) — installed text fit receipts use the same planner as Load, including CPU admission; pre-download quant badges describe VRAM only. Same-slot replacement credits measured resident-private host memory (Linux anonymous RSS / Windows private working set), never mapped GGUF pages or process commit; refusal keeps the running model. The native tier is CPU-only unless its budget covers one expert slot in every routed decode layer. Backend admission plus three-tier placement (Graphics memory / System memory / SSD) for text models (`src-tauri/src/planner/`). `accounting.rs` reads per-tensor sizes from the GGUF header (split GGUFs included), separates routed experts (`ffn_*_exps`) from always-used weights, and sizes KV per token for GQA (exact K/V projection widths), MLA, recurrent/linear-attention fixed state and SWA. `context.rs::context_memory` is the one context-to-memory function (planner, `context_memory` command, UI slider): KV, SWA (capped at window + ubatch), MLA latent, DSA indexer and per-sequence recurrent state with separate K/V types and `-np` slots, plus compute buffers by ubatch and context; it matches llama.cpp b12182's allocator on recorded CPU and CUDA dry runs (`context_tests.rs`: caches exact, compute within ±6 %). For llama-server, context memory and compute come out of graphics memory before the hot-expert cache; an oversized context returns `infeasible_reason` and `max_ctx`. The planner always passes `-np 1` and `-ctk`/`-ctv` through `extra_args`. Placement follows b12182's layer assignment: `-ngl N` counts the output head and MTP blocks first, each offloaded block's caches are charged to the GPU, tied output embeddings count a GPU copy, and partial offload keeps every non-GPU expert on the host with `--cpu-moe` / `--n-cpu-moe`. Blocks are classified the way b12182 does it: `attention.recurrent_layers`, else the arch's `full_attention_interval` default (MiniMax 8, Qwen3-Next/3.5 4), else zero KV heads for the hybrids that use that rule. MiniMax lightning blocks carry a head_dim² state per head. A block it can't positively identify, or a layout it can't size (an unknown recurrent block, attention with no K/V width, Falcon-H1, DeepSeek-V4, Qwen4exp), is refused with a reason, never planned as attention or zero. `force` skips only the eviction offer, never an infeasible plan, and the CPU engine build gets no graphics-memory budget. `hardware.rs` builds the `HardwareProfile` (NVML, sysinfo RAM, models-folder SSD) with default bandwidths; the SSD benchmark is explicit-only (`benchmark_ssd`, at most ~4 GB of a model file). `mod.rs::auto_plan` / `plan` produce a `LoadPlan`: tier bytes, the llama-server args (`--n-cpu-moe`, `--moe-cache-mib`, `--fit off`, ...), warnings, eviction alternative and a speed estimate (`speed.rs`; labels fast ≥ `FAST_TPS` 30, usable ≥ `USABLE_TPS` 8). Measured tok/s from `/metrics` (`runtime.rs`, `subscribe_runtime_stats`) blend into later estimates via `planner.json` (`store.rs`). `load_model` with no explicit `ngl` goes through the planner in the orchestrator's text slot; the OpenAI API's just-in-time loads do too. Commands `hardware_profile`, `benchmark_ssd`, `plan_load`, `context_memory`, `subscribe_runtime_stats`; FitBadge and ModelLoadDialog show the plan; full mock-IPC parity. llama.cpp pin is `b12182` (GLM-5.3-Flash support plus `--moe-cache-mib` / `--cpu-moe`).

Required for Vite HMR + ESM module loader + Tauri 2 IPC bridge to function in `pnpm tauri dev`. **Before the M14 signed-MSI release**, split into dev vs prod CSP (Tauri 2 supports config overlays via `--config`): strip `'unsafe-eval'`/`'unsafe-inline'` and the `ws://` + `http://ipc.localhost` allowances in the production overlay, keeping only `tauri:`, `asset:`, `ipc:`, and the HuggingFace `connect-src`/`img-src` entries.
- **`reqwest::Client` per call** in `validate_hf_token` (`commands/settings.rs`). M5 introduces a shared client in `AppState`; migrate all callers then.
- **No FTS5 sync triggers** in migration `0001_init.sql`. M5 is responsible for keeping `messages_fts` in sync with transcript writes — either via a new migration adding triggers or via app-level inserts in the transcript writer.
- ~~SHA-256 verify on debug builds is software-path only.~~ **Resolved (download-queue/fast-verify PR):** downloads now hash *during* the transfer (`downloader/hasher.rs` frontier hashing — a rolling hasher chases the contiguous completed byte prefix), so the post-download Verifying phase is just the unhashed tail. `sha2` 0.10 already dispatches to SHA-NI at **runtime** (cpufeatures) in every profile; dev builds additionally get `[profile.dev.package.sha2] opt-level = 3` so the compress loop is optimized under `tauri dev`. Deliberately **not** using `-C target-feature=+sha` rustflags: they apply target-wide and statically assume SHA-NI, which crashes on CPUs without the extension (e.g. pre-Ice-Lake Intel desktop parts).
- **M4: engine ZIP SHA-256 pinning.** Engine ZIPs from `ggml-org/llama.cpp` are fetched over TLS but not checksum-verified against a pinned manifest. Ship a `checksums.json` baked into the binary on a future release; tracked debt for the engine updater milestone.
- **M4: CPU RAM-fit estimation.** When no NVIDIA GPU is present, `estimate_model_fit` reports `gpu: false` and a permissive verdict. Refine with `sysinfo`-based system RAM fit when CPU inference is wired in M5.
- ~~M4: GQA fallback table.~~ **Resolved (loader planner):** `planner/accounting.rs` sizes KV from the K/V projection tensor widths in the header, so a missing `head_count_kv` no longer falls back to MHA.
- **M4: engine updater UX.** Engine build is pinned to `b12182` via `ENGINE_BUILD` constant. No in-app update; user reinstalls from `/settings/engine`. Proper update flow is post-M4.
- **M4: graceful llama-server shutdown.** Windows hard-kills via `TerminateProcess` (no graceful SIGTERM equivalent). For long-running sessions in M5, look at sending a stop request to `/shutdown` if llama-server supports it, falling back to hard-kill after a grace window.
- **M4: port allocation race.** `pick_free_port` binds-then-drops; another process can win the port before `llama-server` binds. Mitigation: `wait_ready` will time out and the user retries. Long-term: pass an open socket to the child or use a fixed port range.
- **M4: `EnginePhase` re-export removed.** Slice C dropped `EnginePhase` from the crate-surface re-export in `src-tauri/src/engine/mod.rs` to silence dead-code; the type still lives in `engine::manager`. Re-export when a consumer (M5 chat init?) needs it.
- **M4: `engine_subscribe_status` uses `tokio::spawn`.** `tauri::async_runtime::JoinHandle` doesn't expose `abort_handle()`, mirroring the workaround `subscribe_download_progress` already uses. Revisit if Tauri's async runtime API gains parity.
